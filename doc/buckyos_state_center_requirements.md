# BuckyOS 状态中心需求文档

## 1. 文档目的

本文档用于定义状态中心的需求边界。

它只保留当前已经确认有效的需求，用来约束后续实现，不再保留历史分支讨论。

## 2. 系统定位

状态中心是一个轻量的版本状态服务。

它负责：

- 保存某个 `product + version + os + arch` 对应的构建结果定位符
- 保存该版本的打包状态
- 保存该版本的安装包测试状态
- 保存该版本的发布状态
- 提供“还有哪些版本未打包”“还有哪些版本未测试”的查询能力

它不负责：

- 打包任务分配
- 测试任务分配
- 编译执行
- 打包执行
- 测试执行
- log 保存
- repo / workflow 元数据保存
- 多 `component` 齐套判断

## 3. 权限与安全边界

当前约束已经定稿为：

- 状态中心是单点系统
- 权限模型是发放式
- 可写用户由系统管理员分配
- `users` 表允许保存私钥
- 写接口做签名校验
- 不要求请求时间戳
- 不要求 nonce
- 不把防重放作为首阶段要求

## 4. 数据模型边界

首阶段只要求两张表：

- `users`
- `versions`

其中：

- `versions` 继续采用单表
- 主键为 `product + version + os + arch`
- 一条记录表示一个版本级构建结果及其状态

只有在未来明确需要保留多输入、多轮测试、多轮重试或日志/测试机等细节时，才考虑拆多表。

## 5. `versions` 表需求

`versions` 表至少需要表达：

- `product`
- `version`
- `os`
- `arch`
- `url`
- `commit_sha`
- `packed`
- `pack_tested`
- `published`

说明：

- `url` 不要求是真实 URL
- `url` 只要能被后续脚本识别和消费即可
- 当前不要求把它限定为 `rootfs`

## 6. 状态需求

状态库存储采用整数。

基础语义固定为：

- `0` 未执行
- `1` 成功
- `-1` 失败

如需表达中间态，则增加额外状态码。

当前定稿如下：

### 6.1 `packed`

- `0`：未打包
- `2`：正在打包
- `1`：打包成功
- `-1`：打包失败

### 6.2 `pack_tested`

- `0`：未测试
- `2`：正在测试
- `1`：测试成功
- `-1`：测试失败

### 6.3 `published`

- `0`：未发布
- `1`：发布成功
- `-1`：发布失败

## 7. 覆盖规则

版本号原则上采用 `0.4.1+buildyymmdd` 这一类形式。

业务规则为：

- 正常情况下，一天只保留一个版本
- 特殊情况下同一天可能构建多次
- 这种情况下只保留当天最新的一个

因此，当同一 `product + version + os + arch` 记录被新的 `/version/url` 写入覆盖时：

- 允许覆盖整行
- `tested`、`published`、`packed`、`pack_tested` 全部重置为 `0`

## 8. 查询需求

当前脚本只需要以下查询：

- 哪些版本还没有打包
- 哪些版本还没有测试

因此当前 `GET /version` 只要能支持：

- `nopack=true`
- `notest=true`

就满足首阶段需要。

## 9. 写接口需求

写接口继续沿用当前接口风格，不引入 `v1` 路由。

### 9.1 `/version/url`

用于写入构建结果定位符。

### 9.2 `/version/pack`

用于写入打包状态。

请求语义：

- `packing: true` 表示正在打包
- `packed: true` 表示打包成功
- `packed: false` 表示打包失败

### 9.3 `/version/test`

用于写入安装包测试状态。

请求语义：

- `testing: true` 表示正在测试
- `tested: true` 表示测试成功
- `tested: false` 表示测试失败

### 9.4 `/version/publish`

用于写入发布状态。

请求语义：

- `published: true` 表示发布成功
- `published: false` 表示发布失败

## 10. 当前结论

当前状态中心的正确实现方向已经收敛为：

- 保留 `users + versions` 单表方案
- 保留当前接口风格
- 用布尔输入表达动作，用整数状态码存储结果
- 覆盖同键版本记录时把所有状态位重置为 `0`

后续代码修改应直接对照本文件和 API/schema 定稿文档进行。
